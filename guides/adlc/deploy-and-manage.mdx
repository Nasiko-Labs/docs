Once your agent works locally, deploying it is a matter of connecting to a cluster and running one
command. What happens after that — day-2 operations — uses the same Docker-like command set
regardless of which runtime the cluster uses underneath.

## Connect to a cluster

```sh
nasiko connect https://nasiko.example.com --name prod
nasiko auth login
```

Or start a local cluster instead of connecting to a remote one:

```sh
nasiko up             # starts Postgres, Redis, and the control plane locally, registered as "local"
nasiko clusters        # see all configured clusters
nasiko use prod        # switch the active cluster
nasiko down            # stop the local cluster
```

Every deploy, push, and operate command below runs against whichever cluster is currently active.

## Two ways to get an image onto the platform

Nasiko supports both build-locally-and-push and upload-source-and-let-the-platform-build — pick
whichever fits your workflow:

<Tabs>
  <Tab title="Build locally, push">
    ```sh
    nasiko deploy .                    # build, push, deploy from the current directory
    nasiko deploy . --name my-agent    # explicit name
    nasiko deploy . --port 8080        # non-default container port
    nasiko deploy . --env-file .env    # inject secrets from a file
    nasiko deploy . -e API_KEY=sk-xxx  # inline env vars
    ```

    `nasiko deploy` builds the Docker image locally, pushes its layers and manifest to the
    cluster's embedded registry, and starts (or restarts) the container. Deploying the same agent
    name again updates the existing agent rather than creating a new one — names are unique per
    cluster.

    Need to separate the build from the deploy — for example in CI? `nasiko push .` does steps 1–2
    only, without starting the container.
  </Tab>
  <Tab title="Upload source, let the platform build">
    ```sh
    nasiko upload .
    ```

    No local Docker required. `nasiko upload` zips your source directory (or takes a pre-made
    `.zip`) and posts it to the platform, which builds it on a background build worker and deploys
    the result. You get a build ID back immediately (`202 Accepted`) and can watch progress with
    `nasiko logs` or the platform's Builds view.
  </Tab>
</Tabs>

<Note>
  Every deployment — whichever path you took to get the image there — is automatically
  instrumented for observability and receives its decrypted secrets as container environment
  variables. There's no separate step to wire either of those up.
</Note>

## Day-2 operations

Once an agent is deployed, the command set is deliberately Docker-like:

| Command | What it does |
| --- | --- |
| `nasiko ps` | List running agents (`--json` for machine-readable output) |
| `nasiko logs <agent>` | Tail container logs (`-n 200` for more history) |
| `nasiko stop <agent>` | Scale to zero, keeping configuration and state |
| `nasiko start <agent>` | Resume a stopped agent |
| `nasiko restart <agent>` | Destroy and recreate the container, picking up any secret or env changes |
| `nasiko scale <agent> <n>` | Scale to `n` replicas |
| `nasiko rm <agent>` | Terminate and deregister (`-f` skips the confirmation prompt) |
| `nasiko status` | Control plane health and metrics |

<Warning>
  `restart` and `stop`/`start` aren't interchangeable. `restart` tears down and recreates the
  container — it's what picks up secrets or environment variables you've changed since the last
  deploy. `stop`/`start` just pause and resume the existing container without touching
  configuration.
</Warning>

## Secrets

Secrets are encrypted environment variables injected into your agent's container at deploy and
restart time, at two scopes:

```sh
# Vault secrets — applied to every agent you own
nasiko secrets set OPENAI_API_KEY sk-xxx
nasiko secrets ls
nasiko secrets rm OPENAI_API_KEY

# Agent-specific secrets — override the vault, applied to one agent only
nasiko secrets set DB_URL postgres://... --agent my-agent
nasiko secrets ls --agent my-agent
```

Precedence, highest wins: an inline `nasiko deploy -e` flag beats an agent-specific secret, which
beats a vault secret. Changing a secret doesn't take effect until you `nasiko restart` the agent —
see the [secrets overview](/guides/secrets/overview) for the full model, including how it interacts
with per-team and per-department scoping.

## Observability

```sh
nasiko observe               # sessions, trace/span detail, project stats, FinOps dashboard, insights
```

Every deployment is auto-instrumented, so traces, logs, and cost data are available the moment your
agent starts handling traffic — see [the orchestrator](/platform/orchestrator) for how a session
groups a multi-agent conversation into one trace.
