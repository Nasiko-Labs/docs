---
title: "Managing your agent's secrets"
description: "Set, inspect, and rotate encrypted secrets for your own agents via the CLI or API"
---

Agents frequently need credentials of their own — a third-party API key, a database connection
string, an internal service token. Nasiko lets you attach these as **secrets** scoped to an
agent (or shared vault-wide), stores them AES-256-GCM encrypted at rest, and only decrypts them
into the container's environment at deploy time. See
[Secret management overview](/guides/secrets/overview) for how the encryption itself works.

## Setting secrets with the CLI

The `nasiko secrets` command manages secrets from your terminal:

```bash
# Set a secret scoped to a specific agent
nasiko secrets set STRIPE_API_KEY sk_live_xxxxx --agent my-billing-agent

# Set a vault-wide secret (available to any agent you deploy)
nasiko secrets set OPENAI_API_KEY sk-xxxxx

# List secret names (values are never echoed back)
nasiko secrets ls --agent my-billing-agent

# Read a secret's metadata
nasiko secrets get STRIPE_API_KEY --agent my-billing-agent

# Remove a secret
nasiko secrets rm STRIPE_API_KEY --agent my-billing-agent
```

Secrets set without `--agent` live at the vault level and can be referenced by any agent you
deploy; secrets set with `--agent` are scoped to that agent only.

## Managing secrets with the API

The same operations are available over the `/api/secrets/*` route group for anything scripting
against the control plane directly rather than going through the CLI. As with the CLI, calls are
authenticated and scoped to either the vault or a specific agent.

## Who can manage secrets

Setting, reading, or removing secrets requires the `can_manage_secrets` permission. See
[Access control overview](/guides/acl/overview) for the full role hierarchy and how permissions
map onto roles — this page doesn't duplicate that model.

## How secrets reach a running agent

Secrets aren't mounted as files or fetched by the agent at runtime — they're decrypted server-side
and injected as environment variables at deploy time, alongside the observability configuration
that instruments every container automatically. From the agent's point of view, a secret is just
an environment variable that happens to be there when the process starts.

This has one important consequence for updates:

<Warning>
  Changing a secret's value doesn't affect a container that's already running. Restart the agent
  (`nasiko restart`) to pick up the new value — the restart re-reads the current secret set and
  re-injects it into the container environment.
</Warning>

## Secret refresh on scale-up

When an agent scales to more replicas, Nasiko refreshes its secrets immediately before the new
replicas start, so every replica — old and new — is running with the current secret values
rather than whatever was current at original deploy time. You don't need to manually restart an
agent after rotating a secret and then scaling it; scaling up is itself a refresh point.
