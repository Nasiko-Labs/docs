Agents reach external tools — Gmail, Slack, GitHub, a custom internal API — through Nasiko's MCP
gateway, described in [MCP overview](/mcp-hub/overview). This page covers the access-control
layer on top of that gateway: **per-agent connector and tool permissions** — a control that's
independent of both mechanisms on the other ACL pages. It doesn't change who can chat with an
agent ([user → agent access](/onboarding/acl/user-agent)) or which agents can call each other; it
controls what a given agent is allowed to *do* once it's running — specifically, which connectors
it may use and which individual tools within them.

## Two layers, checked in order

Every tool call an agent makes resolves through two layers, always checked in this order:

1. **Reachability** — can the calling user reach this connector at all? A connector is reachable if
   the user owns it, or it's been shared with them (by username, or with an explicit grant to
   their team or department), or — for a platform-managed integration like a Composio toolkit —
   it's globally available and the user simply connects their own account. A connector that fails
   this check is invisible: it doesn't appear in the tool list at all, regardless of any per-agent
   rule that might otherwise allow it.
2. **Per-agent permission** — assuming the connector is reachable, is it enabled for *this specific
   agent*, and is the specific tool being called allowed?

Layer 2 is never consulted unless Layer 1 already passed. A connector a user no longer has access
to can't be reactivated for an agent just because an old per-agent rule was never cleaned up — the
reachability check is re-evaluated on every single call, not cached past a permission change.

## Default-allow, not default-insert

Per-agent permission works opposite to most allowlist systems: **no configuration means fully
allowed.** Nothing needs to be written to grant an agent access to a connector that the calling
user can already reach — sharing a connector with someone makes it usable on every agent they run,
immediately, with zero extra setup. A permission row only ever exists to *restrict* something:
disable a connector entirely for one agent, or apply a specific allow/ask/block rule to one or more
of its tools.

Three stances are available per tool:

| Stance | Effect |
| --- | --- |
| `allow` | The tool can be called normally (the default when no rule matches) |
| `ask` | The call is blocked and reported as requiring approval, rather than executed |
| `block` | The call is rejected outright |

Rules are expressed as glob patterns against tool names, so one rule can cover a whole family of
operations:

```json
{
  "enabled": true,
  "tool_rules": [
    { "pattern": "SEND_*", "stance": "block" },
    { "pattern": "READ_*", "stance": "allow" },
    { "pattern": "DELETE_*", "stance": "ask" }
  ]
}
```

This example leaves a connector enabled for an agent but blocks every tool starting with `SEND_`
(for example, an email-send action), explicitly allows every read-only tool, and requires approval
before any delete-style tool runs.

## Configuring it

**View an agent's current connector access:**

```
GET /api/mcp/agents/{agent_id}/connectors
```

**Enable, disable, or set tool rules for one connector on one agent:**

```
PUT /api/mcp/agents/{agent_id}/connectors/{connector_id}
```

```json
{
  "enabled": true,
  "tool_rules": [
    { "pattern": "SEND_*", "stance": "block" }
  ]
}
```

**Inspect a connector's tools and their effective stance for that agent:**

```
GET /api/mcp/agents/{agent_id}/connectors/{connector_id}/tools
```

**View or bulk-update every tool rule for an agent, across all its connectors:**

```
GET /api/mcp/agents/{agent_id}/tools
PUT /api/mcp/agents/{agent_id}/tools
```

**Reset an agent back to fully default-allow**, clearing every override at once:

```
DELETE /api/mcp/agents/{agent_id}/permissions
```

Configuring an agent's connector access requires the ability to manage that agent (its owner, or a
superuser) — the same requirement covered in [user → agent access](/onboarding/acl/user-agent) — *or*,
more narrowly, reachability to the connector itself once it has already been granted to that
agent. That narrower path lets someone who merely has a connector shared with them enable or
adjust it on any agent it's already attached to, without handing them any other control over that
agent.

## Sharing a connector with a team or department

Connector owners share by username through the regular MCP connector-sharing routes (see
[MCP overview](/mcp-hub/overview)). Sharing with an entire team or department is an admin
operation:

```bash
nasiko-ee access mcp share <connector-id> --team platform-eng --dept engineering
nasiko-ee access mcp unshare <connector-id> --team platform-eng
```

To see everything currently consuming a connector — which agents have it enabled, which users
have a direct grant, and which teams/departments share it — use:

```bash
nasiko-ee access mcp consumers <connector-id>
```

<Note>
  Revoking a share doesn't just stop future access — it also removes the grantee's own stored
  credential for that connector, so a later re-grant always starts from a clean reconnect rather
  than silently reactivating a stale session.
</Note>
