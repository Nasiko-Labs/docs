This page covers the first of the two access-control mechanisms described in the
[access control overview](/onboarding/acl/overview): which people can reach a given agent, and what
they're allowed to do to it once they can.

## Two different questions

Every check against an agent actually asks one of two separate questions:

1. **Can this user reach the agent at all?** — proxying a chat request to it, viewing it in a
   catalog, listing its details.
2. **Can this user change or destroy the agent?** — updating its configuration, deleting it,
   viewing or rotating its secrets.

The second question is deliberately stricter than the first. Being able to chat with an agent —
because it's public, or shared with your team — never by itself grants the right to modify or
delete it. Only the agent's **owner**, or a **superuser**, can do that. This distinction matters in
practice: publishing an agent broadly, or granting your whole department access to it, doesn't
hand any of those people management rights over it.

<Warning>
  A soft-deleted agent is always denied to everyone except through direct database recovery — no
  ownership, grant, or public flag overrides a deletion.
</Warning>

## What grants view/chat access

A user can reach an agent (question 1 above) if **any** of the following is true:

| Condition | Description |
| --- | --- |
| Ownership | The user created the agent |
| Team ownership | The agent is assigned to a team the user belongs to |
| `is_public` | The agent's public flag is set — anyone on the platform can reach it |
| Explicit grant | A grant exists naming the user, a team they're in, a department they're in, or `*` for everyone |

Grants are additive: an agent can be privately owned by one person and still be reachable by an
entire department through a grant, without changing its ownership or its public flag. A public
agent (`is_public`) and an organization-wide grant are similar but distinct — `is_public` extends
to anyone the platform's routing surfaces reach, while an organization grant is scoped to your
platform's own authenticated users.

## Managing grants

Grant and revoke access from the admin CLI, or the equivalent API routes, addressed to the target
agent:

```bash
# Grant a specific user, a whole team, and a whole department in one call
nasiko-ee access grant <agent-id> --user alice --team platform-eng --dept engineering

# Make the agent public
nasiko-ee access grant <agent-id> --public

# Revoke a user's access without touching the team/department grants
nasiko-ee access revoke <agent-id> --user alice

# Revoke the public flag (make the agent private again)
nasiko-ee access revoke <agent-id> --public
```

`--user`, `--team`, and `--dept` each accept multiple values and can be combined in a single grant
or revoke call. An agent can also be granted directly to *another agent*, which is a distinct
mechanism from the agent-to-agent allowlist described in
[access control overview](/onboarding/acl/overview) — it controls whether a human acting through that
other agent's context can reach this one, not whether the two agents may call each other
programmatically.

Inspect current access:

```bash
nasiko-ee access ls <agent-id>              # resolved users + agent grants
nasiko-ee access visibility <agent-id>      # is_public flag + every raw grant, grouped by type
nasiko-ee access list-users <agent-id>      # every user who currently has access
nasiko-ee access dept-grants <agent-id>     # departments with an explicit grant
nasiko-ee access team-grants <agent-id>     # teams with an explicit grant
nasiko-ee access accessible-agents <agent-id>   # agents this agent can reach
nasiko-ee access my-agents                  # agents the current user can reach (owned + shared)
nasiko-ee access user-agents <user-id>      # agents a specific user can reach (admin only)
```

### Example: sharing an agent with one team, keeping it private otherwise

```bash
nasiko-ee access grant a1b2c3d4 --team platform-eng
nasiko-ee access visibility a1b2c3d4
```

```
Agent 'a1b2c3d4' visibility:
  Public: no

  user grants (0):
    (none)

  team grants (1):
    <platform-eng-team-id>

  department grants (0):
    (none)

  agent grants (0):
    (none)
```

The agent stays private (`is_public: no`), but every member of the `platform-eng` team can now
chat with it — nobody outside that team can, unless they own it or another grant is added.

## Managing an agent

Update, delete, rename, transfer ownership, or reassign an agent's team/department — all of which
require ownership of the agent or superuser privileges, not merely view/chat access:

```bash
nasiko-ee access rename <agent-id> "new-name"
nasiko-ee access owner <agent-id> <new-owner-user-id>        # transfer ownership
nasiko-ee access org <agent-id> --team platform-eng --dept engineering
```

Managing an agent's secrets follows the same ownership-or-superuser rule, gated additionally by the
`team_lead`-and-above role threshold described in
[access control overview](/onboarding/acl/overview) — see [secret management](/platform/secret-manager/overview)
for the full secrets workflow.
