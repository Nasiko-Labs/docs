---
title: "Secret management overview"
description: "How Nasiko protects agent secrets and platform identity credentials"
---

Nasiko handles two distinct categories of sensitive material: the **per-agent secrets**
developers attach to their own agents (API keys, database credentials, third-party tokens),
and **platform-level identity secrets** used to authenticate users into Nasiko itself (SSO
client secrets, session signing keys). Both are encrypted at rest and never appear in plaintext
outside the moment they're needed.

## Per-agent secrets

Every secret you attach to an agent is encrypted at rest with **AES-256-GCM** before it's
written to the database. Nasiko only decrypts a secret when it's injected into the agent's
container environment at deploy time — the plaintext value exists in memory for the duration
of that deploy call and then inside the running container, never anywhere else.

This means:

- Secrets are stored ciphertext-only. A database dump or backup never exposes raw values.
- Decryption happens once, server-side, immediately before the container starts.
- Rotating a secret and restarting the agent re-injects the new value; nothing is cached
  outside the container's own environment.

<Warning>
  The encryption key used for this scheme (`SECRETS_ENCRYPTION_KEY`) is a 32-byte, base64-encoded
  value that the platform validates at startup — the server refuses to start if it's missing or
  malformed. Treat it like any other root secret: generate it with a cryptographically secure
  random source, store it in your secrets manager (not source control), and rotate it
  deliberately — rotating it invalidates every secret encrypted under the old key, so all
  agent secrets must be re-entered after a rotation.
</Warning>

See [Managing your agent's secrets](/platform/secret-manager/user-secrets) for the CLI and API workflow,
including who can set them and how they behave across scaling events.

## Platform identity secrets

Separately, Nasiko supports **SSO login** through any OIDC-compliant identity provider (Entra
ID, Okta, Auth0, Keycloak, and others). The client secret issued by your identity provider is
itself encrypted at rest using the same AES-256-GCM scheme, whether you configure it via
environment variables at deploy time or through the admin settings API at runtime.

See [Setting up SSO login](/platform/secret-manager/entra-id) for the full configuration walkthrough,
including how group claims from your identity provider can automatically place users into
roles, teams, and departments.

## Where this fits

Secret management is one piece of Nasiko's broader access model — who can deploy agents, who
can read their secrets, and who can call them. For the full picture of roles and permissions,
see [Access control overview](/onboarding/acl/overview). For how secrets flow into a running
container as part of a deployment, see [Agents](/platform/agent-registry).
